# API_GLACCOUNTLINEITEM Skill

## Purpose

Use this API for G/L Account Line Items - Read (A2X), not for standalone ledger master records. This service enables you to retrieve accounting-specific information from all journal entries in Financials. You can read journal entry items and detailed information for ledger, company code, ledger fiscal year, G/L account and optionally segment, profit center, cost center and other fields.

Keep `data/index/API_GLACCOUNTLINEITEM` as the schema ground truth. This skill provides business usage guidance only. This index was built from SAP metadata plus OpenAPI documentation.

## When To Use

- The user asks about g/l account line items - read (a2x) or the business objects exposed by this service: GLAccount Line Item.
- The request is read-oriented and can be answered from entity sets and fields indexed under `data/index/API_GLACCOUNTLINEITEM`.
- Prefer this API when the user language clearly matches the service title, entity names, or documented field descriptions.

## When Not To Use

- Do not use this API for unrelated master data or transactions that belong to a more specific API already available in the catalog.
- Do not use this API for write, create, update, delete, release, cancel, or action execution in normal read-only query planning unless the user explicitly asks and the application mode allows it.
- Do not invent fields, entities, joins, or business conclusions beyond the indexed schema and this skill.

## Key Entities

- `GLAccountLineItem`: Get entities from GLAccountLineItem. Methods: GET. runtime metadata available.

## Business Semantics

- Primary business scope: G/L Account Line Items - Read (A2X).
- Use the service description, entity descriptions, and field descriptions from `data/index/API_GLACCOUNTLINEITEM` to infer user intent.
- Use `GLAccountLineItem` for journal-entry line-item reporting when the wording is anchored to a G/L account, general ledger, ledger, clearing state, fiscal period, or another G/L-account-specific dimension, together with company code, accounting document, posting date, amounts, quantities, reference documents, assignments, or partner/service-document fields. The presence of `journal entry` wording alone is not enough to make this a G/L-account line-item request.
- Prefer this API for G/L account activity detail, open item, cleared item, and clearing-status questions. Chinese wording such as `总账科目...发生明细`, `总账科目的未清项目`, `还没有清账的项目`, `已清项目`, or `清账日期` should stay on `GLAccountLineItem` because this service exposes `PostingDate` and `ClearingDate`.
- When a user combines G/L account balance wording with open-item wording, such as `科目...余额` plus `未清项目日期`, treat it as an open-item balance as of a key date, not as a trial balance request.
- For balance drilldown wording such as `余额下钻`, `从余额下钻查看凭证明细`, or `drill down from G/L account balance to line items`, use companion API `C_TRIALBALANCE_CDS` with `API_GLACCOUNTLINEITEM`: first establish the balance scope, then query `GLAccountLineItem` for the underlying accounting document line items.
- For fiscal-period drilldown wording such as `2023年第12期`, prefer `GLAccountLineItem.FiscalYear` plus `GLAccountLineItem.FiscalPeriod` filters over approximating the period with `PostingDate` ranges. Select `FiscalPeriod` and `FiscalYearPeriod` when period context is part of the answer.
- Do not use this API when the user asks for journal entry item master-data names such as company code name, cost center name, or profit center name on journal entry items; route those requests to `API_JOURNALENTRYITEMBASIC_SRV`, which exposes `CompanyCodeName`, `CostCenterName`, and `ProfitCenterName`.
- Do not use this API for generic `日记账行项目`, `会计凭证项目`, or `财务行项目` requests that do not include a G/L-account, general-ledger, ledger, clearing-status, or open-item qualifier. Route those universal journal-entry requests to `API_JOURNALENTRYITEMBASIC_SRV`.
- Do not use this API for standalone ledger master data, ledger names, or ledger configuration records. Route those requests to `API_LEDGER_SRV` when available.
- Do not use this API for accounting exception queries such as `手工凭证`, `凭证类型`, `过账用户`, or `大额总账项目`; route those to `API_OPLACCTGDOCITEMCUBE_SRV`, which exposes accounting document type, creator, and amount fields for operational accounting items.
- For wording such as "include", "show fields", or "with ... details", treat named concepts as `$select` fields, not as filters. Do not invent placeholder filters for fields such as `GLAccountLineItem.AccountingDocCreatedByUser` unless the user supplies a concrete user name.
- For created-by-user, account assignment, reference document, service document, clearing, amount, quantity, and organization questions, keep the query on `GLAccountLineItem` and select the requested fields.
- For all `GLAccountLineItem` record/list/line-item outputs, do not return `GLAccountLineItem.ID` as an answer or main output field. It is a technical CDS/OData key and can contain generated composite text rather than a business identifier. Keep stable row-identifying dimensions in `$select`: CompanyCode, FiscalYear, AccountingDocument, AccountingDocumentItem, Ledger, and GLAccount.
- Use this API for supplier/customer open-item and cleared-item detail when the user asks for `未清项目`, `已清项目`, `清账关系`, `清账日期`, `还没收款清账`, `供应商未清行项目`, or `客户未清行项目`. For generic G/L open items, filter open items with `ClearingDate eq null`; filter cleared items with `ClearingDate ne null`. For FBL1N-style supplier AP open items, also apply the supplier AP filters described below.
- For a specific journal-entry clearing relationship/status request, keep all line items in scope. Filter only by the supplied document identifiers such as `CompanyCode`, `FiscalYear`, and `AccountingDocument`; select `ClearingDate`, `ClearingAccountingDocument` if available, `ClearingDocFiscalYear`, and the stable row-identifying dimensions. Do not add `ClearingDate ne null` unless the user explicitly asks for only cleared items; null clearing fields are part of the answer for uncleared lines.
- For reference-document tracing wording such as business reference document, source document, originating document, or FI document generated from a business reference, use `GLAccountLineItem.ReferenceDocument` when the user provides a document number and asks for accounting line items. Select `ReferenceDocument`, `CompanyCode`, `FiscalYear`, `FiscalPeriod`, `AccountingDocument`, `AccountingDocumentItem`, `Ledger`, `GLAccount`, posting/document dates, and amount fields. Do not ask the user to classify the source business document type first when the requested output is FI/accounting line items; `ReferenceDocument` is the broad first-pass trace field for this API.
- For supplier AP detail, filter/select `Supplier`. For customer AR detail, filter/select `Customer`. Include `CompanyCode`, `FiscalYear`, `AccountingDocument`, `AccountingDocumentItem`, `Ledger`, `GLAccount`, `PostingDate`, `ClearingDate`, and `AmountInCompanyCodeCurrency` as stable output context.

- For `特殊总账` requests, select/filter `SpecialGLCode`; use `SpecialGLCode ne ''` when the user asks for all special G/L items without specifying an indicator.
- For FBL1N-style supplier payable line-item wording such as `供应商未清项目`, `未清应付项目`, `供应商已清项目`, `已经清账的应付项目`, or `供应商特殊总账项目`, use `GLAccountLineItem` directly. Do not ask the user to choose between invoice, GR/IR, and supplier account views when the request is for supplier AP line-item detail with company code and supplier filters.
- For FBL5N-style customer receivable line-item wording such as `客户未清项目`, `未清应收项目`, `客户已清项目`, `已经清账的应收项目`, or `客户特殊总账项目`, use `GLAccountLineItem` directly. Do not ask whether the user means customer master settings or transaction detail when the request includes company code and customer filters.
- For receivable analysis by sales organization, customer group, or profit center, select `SalesOrganization`, `CustomerGroup`, and `ProfitCenter` on `GLAccountLineItem`; aggregate `AmountInCompanyCodeCurrency` only when the user asks for totals or analysis rather than document-level detail.
- Do not use this API as the primary API for AP/AR aging, overdue, net due date, or payment-block questions when `API_OPLACCTGDOCITEMCUBE_SRV` is available; that API exposes `NetDueDate`, `PaymentBlockingReason`, and payment-term fields. - Preserve SAP document numbers, item numbers, partner numbers, material/product IDs, company codes, plants, fiscal years, dates, currencies, quantities, statuses, and type codes exactly as returned by SAP.
- When a user asks for a list, prefer the entity whose business level matches the requested object: header for document headers, item for line items, schedule for schedule lines, partner/address/text/pricing/account entities only when those details are explicitly requested.
- For boolean fields, use unquoted OData boolean literals `true` and `false`. For string indicator fields, preserve the string literal exactly.
